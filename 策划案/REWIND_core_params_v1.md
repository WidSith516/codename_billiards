# REWIND · 核心物理参数锁定表（v1）

> 目的：**消除实现者与求解者各自猜参数的协调风险**。
> `godot/` 的实现、`tools/solver/` 的求解器、以及后续关卡设计**必须使用同一组参数**，
> 否则「求解器说可解」与「游戏里可解」会是两件不同的事。
>
> 状态：**已锁定（Lead 决策）**。任何改动都需同步更新本文件，并在 `godot/DIFFERENCES.md` 记录。

---

## 0. 为什么要有这份文件

实测（`tools/h5harness/REPORT.md`）证明 H5 原型的物理常量组合是**不可用**的：
库边 ×1.5 是不稳定不动点、指数阻尼滑行 1167 px、历史采样与步长耦合。
迁移到 Godot 时必须**一次性换成有界、可预期、可测试**的模型。

但换模型有第二个风险：**每个人换的数值不一样**。本文件消除这个风险。

## 2. 击球（唯一一杆）

| 参数 | 值 | 依据 |
|---|---|---|
| 力度上限 `POWER_MAX` | **170**（拖拽像素） | 沿用 H5 |
| 速度系数 `SPEED_PER_POWER` | **7.4** | 沿用 H5 |
| **最大初速 `V_BREAK`** | **1258 px/s**（=170×7.4） | 沿用 H5 |
| 最小有效拖拽 | 12 px | 沿用 H5 |

**尺度检验**：1258 px/s ÷ 428 px/m ≈ **2.94 m/s**。

这可以接受（球桌也偏小），但意味着**手感偏“软”**；若要更接近真实重击，
需同时提高 `SPEED_PER_POWER` **并**按 §3 重算摩擦。**本版不改，先保持一致。**

## 3. 滚动摩擦：**常量减速度**（替换 H5 的指数阻尼）

```text
每步：v -= A_FRICTION * dt
若 v 与运动方向相反（即越过零）→ v = 0（硬停，不做反向）
```

| 参数 | 锁定值 | 说明 |
|---|---|---|
| **`A_FRICTION`** | **640 px/s²** | 见下方推导 |

**推导（目标：手感对齐 H5 的“一杆约 1.3 个桌长”，但物理上是常量减速度）**

- H5 指数阻尼在满力下实际滑行 **1167 px = 1.28 个桌长**（实测，见附录 A）。
- 常量减速度下走同样距离需要 `A = v²/(2d) = 1258²/(2×1167) = **678 px/s²**`。
- 取整并留出更短的尾段（避免长距离“无摩擦漂移”感），锁定 **640 px/s²**。
- 校验：`d = 1258²/(2×640) = **1236 px** = **1.36 个桌长**；停稳时间 `1258/640 = **1.97 s**`。

**尺度检验**：640 px/s² ÷ 428 px/m = **1.50 m/s²**。
真实台呢滚动摩擦约 0.2–0.4 m/s²，但真实球速 7 m/s 时同样只走 2–3 个桌长——
差异来自本作球速偏低（§2）。**结论：手感正确，尺度解释力有限，属于可接受的有意近似。**
若要更“台球”，需同时把 `V_BREAK` 提到 ~2000 px/s 并把 `A_FRICTION` 提到 ~2500 px/s²，
**但那会撞上 §5 的穿透约束**，故本版不做。

## 4. 库边（替换 H5 的无界 ×1.5）

```text
撞库后：v_reflected = reflect(v, n)
       |v_reflected| = min(|v_reflected| * WALL_RESTITUTION + WALL_GAIN, V_CAP)
```

| 参数 | 锁定值 | 说明 |
|---|---|---|
| 目标球 `WALL_RESTITUTION` | **0.92** | 略小于 1，自然损耗 |
| 目标球 `WALL_GAIN` | **0** | 目标球不获得能量 |
| **白球 `WALL_RESTITUTION`** | **0.92** | 与目标球相同 |
| **白球 `WALL_GAIN`** | **120 px/s** | 每次撞库的**固定**增量（白球专属收益） |
| **`V_CAP`（硬上限）** | **2000 px/s** | 所有球，任何情况 |

**为什么是这个形状**：
- **乘法换加法**：H5 的 `v *= 1.5` 是不稳定不动点 `v* = kL/ln1.5`（短飞时阈值仅 540 px/s，
  而出杆 1258 px/s 已远超）⇒ 必然发散。改成 `v*0.92 + 120` 后，
  **驻点 = 120/(1-0.92) = 1500 px/s**，低于 `V_CAP` ⇒ **数学上不可能发散**。
- 玩家收益仍是可感知的：持续撞库能把白球维持在 ~1500 px/s，
  即「单杆输入 + 库边持续供能」，符合策划案 §5.2 的设计意图。
- `V_CAP = 2000 px/s` 留出安全边际：最坏情况斜向碰撞的安全界是 2070 px/s（见 §5）。

**必须做的断言**：满力击球后跑 60 s，**任何球的速度不得超过 `V_CAP`，且不得出现 `Infinity`/`NaN`**。

## 5. 碰撞：必须用连续碰撞，不能只靠压速度

| 项 | 决策 |
|---|---|
| 球-球恢复系数 `BALL_RESTITUTION` | **0.955**（沿用 H5，等质量） |
| 球-球 | 近似弹性；**解析求首次接触时间（TOI），按 TOI 推进并结算**，不做「先位移再检测」 |
| 库边 | 同样按 TOI 处理 |
| 单帧多次库边接触 | **一次步内无论接触几条库，只施加一次 §4 的变换**（与 H5 的「同帧只加成一次」一致，但本版该分支**必须可达**——见下方袋口变更） |
| 子步 | 若单步位移 > 最小碰撞弦长，必须细分；**细分依据是弦长，不是固定次数** |
| 重叠 | 允许极小重叠 + 位置修正；**修正不得引入额外动量** |

**为什么不能只压速度（实测依据）**：`STEP=1/120` 时，**擦撞远比正撞脆弱**——
碰撞参数 `b=23.5`（弦长仅 13.13 px）时，**1900 px/s 就漏判 41.7%**，
而正撞要到 5856 px/s 才 50% 漏判。因此「把速度压到 2928 以下」**不足以**消除穿透。
（数据：`tools/h5harness/REPORT.md` D-13；复现 `node tools/h5harness/diag5.mjs`）

**袋口判定变更**：H5 用「球心距袋心 < 24」的点判定，导致球可能**掠过**袋口而不进，
也导致 T08b（同帧双库只加一次 ×1.5）成为**死代码**（双库接触点距角袋心 17.25 px < 24，
`inPocket()` 先执行必然入袋）。
→ 本版改为：**袋口是一个圆（袋心 + 半径），球心进入该圆且速度方向指向袋内 ⇒ 入袋**；
并把双库接触点从袋口捕获区中**显式排除**（或用「速度朝向袋心」条件自然排除），
使 T08b 成为**可达的**测试用例而非死代码。

## 6. 回溯（本作最核心的语义，不得偏离）

沿用策划案 §4.1/§4.2 的定义，以下为**实现约束**：

| 项 | 决策 |
|---|---|
| 记录对象 | **仅白球**（策划案 §4.1，用户已确认不改） |
| 采样 | **固定弧长间隔** `HISTORY_STEP_PX = **2.0 px**`，每条记录存 **位置 + 速度** |
| 记录触发 | 白球实际位移累计 ≥ 2.0 px 时追加一条；**不按帧数记录** |
| **回溯推进速率** | **`REWIND_CRAWL_PX_PER_S = 240`**（= 2.0 px / (1/120 s)），即**每物理步回退一条记录** |
| 回溯读取 | 开始时对当前历史做**只读快照**；游标反向移动 |
| 回溯期间主历史 | **继续追加**（保证 A→B→C→D，下次可 D→C→B→A）——GDD §4.1 的核心 |
| 回溯位置 | 由快照**强制决定**，其他球不能阻挡或偏转白球 |
| 释放速度 | **直接取该记录里存的 `v` 取反**；**禁止**用位置差求导（H5 的步长耦合缺陷） |
| 到达历史起点 | 自动停止，速度归 0 |

### 6.1 ⚠️ 必须分清的两件事：**回放「位置爬行速率」≠「释放速度」**

这是本表 v1 未写明、由 `m1-solver` 指出的一处歧义，现予以明确：

| 量 | 取值 | 用途 |
|---|---|---|
| **位置爬行速率** | **固定 240 px/s**（每步回退 1 条 × 2.0 px） | 决定「按住 R 多久能退多远」 |
| **速度（记录值 `v`）** | 该历史点**当初的真实速度**（满力时最高 1258 px/s） | 决定 §7 的碰撞冲量、以及松手后的释放速度 |

两者**刻意解耦**，这是设计选择，不是疏漏：
- 若让爬行速率也等于记录速度，则**回溯会按原始速度曲线忽快忽慢**，且高速段几乎无法精细控制
  （满力时 10 px/步，玩家一帧就错过落点）；
- 固定 240 px/s 使「按住 N 秒 ≈ 倒退 N 秒」**可预期**，这正是 §6 想要的直觉，
  也正是 H5「忽快忽慢」缺陷的修复目标。

**代价（必须记录）**：满力路径 1236 px 需 `1236/240 = **5.15 s**` 才能退到底。
这偏长，但**本作不需要退到底**——玩家只需退到想释放的那个位置，通常 1–2 s。
**待实测**：5.15 s 的最大回溯时间是否影响手感；若影响，优先调节
`REWIND_CRAWL_PX_PER_S`（提到 480 则满力路径 2.6 s），**而不是**改回速度耦合。

> **注意区分两个不同的“预算”概念**，不要混淆：
> - `HISTORY_STEP_PX` / `REWIND_CRAWL_PX_PER_S` 是**采样与回放速率**（本表已锁定）；
> - 「每关可回溯多少距离/几次」是**关卡预算**（策划案 §4.2 的资源设计，**尚未定案**，
>   见 §8 待决策问题 1）。二者独立：前者是机制常数，后者是关卡参数。

**为什么 `HISTORY_STEP_PX = 2.0`**：H5 的「位移 > 1e-5 就记一条」导致记录点间距极不均匀
（中位 0.0996 px，最大 10.39 px），于是回溯回放忽快忽慢、轨迹折线切弯道。
2.0 px 的均匀采样使：①回放速率可预期；②轨迹绘制不需抽样即可保真
（H5 的 `sample = len/140` 会把弯道切掉）；③历史体积有界
（60 s × 1500 px/s ÷ 2 px ≈ 45k 条上限）。

## 7. 回溯碰撞冲量（修正 H5 的放大与方向缺陷）

```text
n = 从白球指向目标球的单位法向
v_rel = (v_cue - v_target) · n
j = max(0, v_rel) * REWIND_IMPULSE_K
target.v += n * j          // 沿法向给目标球
// 白球速度不因该碰撞改变（它必须沿历史轨迹运动）——GDD §4.4 第 1 条
```

| 参数 | 锁定值 | 说明 |
|---|---|---|
| **`REWIND_IMPULSE_K`** | **1.0** | 不得 > 1（H5 用 1.6 会凭空增能） |

**两个必须修正的缺陷**：
1. **不得放大**：H5 的 `kick = min(1300, 1.6*rel)` 让目标球获得**超过**白球相对速度的冲量。
2. **擦撞必须弱于正撞**：H5 的 `rel` 只用白球速度与法向的点积，与**接触几何**无关，
   导致擦撞与正撞给一样大的推离速度。`j = max(0, v_rel)·n` 中 `v_rel` 已含法向投影，
   因此**薄球自然给得少**，符合台球直觉，也让「改变接触点」成为玩家的有效杠杆。

**注意**：本模型下回溯撞击**不守恒**（白球不减能），这是 GDD §4.4 有意定义的**游戏规则**，
不是缺陷；但**不得放大**——玩家的能量来源只应是击球与库边增量，不能是回溯撞击。

## 8. 参数总表（实现者请直接引用）

```csharp
// godot/src/Core/PhysicsConfig.cs  —— 以下为锁定值，改动须同步本文件
public const float BallRadius       = 12.2f;   // px
public const float TableLeft        = 65f;

public const float BallRestitution  = 0.955f;  // ball-ball, equal mass (carried from H5)

public const float ObjectBallGain   = 0f;
```
